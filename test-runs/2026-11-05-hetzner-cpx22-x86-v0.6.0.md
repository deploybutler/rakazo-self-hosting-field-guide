# Test run: 2026-11-05 — Hetzner CPX22 (x86_64, Ubuntu 24.04) — Rakazo v0.6.0 fresh install (test 4)

- **Date (Europe/Berlin):** 2026-11-05
- **Tester:** DeployButler
- **Provider / machine type:** Hetzner **CPX22** (2 vCPU AMD / 4 GB RAM / 80 GB SSD), Falkenstein data center
- **Architecture:** x86_64
- **Operating system:** Ubuntu 24.04.4 LTS
- **Docker:** 29.9.3 (client and server), Docker Compose v5.7.0 — installed fresh via the official `get.docker.com` script, which took **31 seconds**
- **Rakazo release / channel:** v0.6.0 published images (`RAKAZO_IMAGE_TAG=v0.6.0`, `RAKAZO_COMPUTER_IMAGE_TAG=v0.6.0`, set in `.env` after `--prepare-only`, before first start)
- **Scenario:** Fresh install on a blank x86 machine — the x86 counterpart of test 2 (arm64), at stack level per the standing test plan (no bot conversation, no model-provider key).

## Machine choice, recorded honestly

The preferred x86 sizes for a like-for-like comparison with the arm64 row (CX33, and CPX32 as the regular-performance equivalent — 4 vCPU / 8 GB) were **out of stock in both Nuremberg and Falkenstein** on the day. The maintainers approved the CPX22 as the floor spec for this row; a CPX12 (1 vCPU / 2 GB) was explicitly rejected because the stack's measured idle footprint (about 1 GiB of container memory, see test 2) plus a browser sandbox would not leave enough headroom to attribute any failure cleanly. So this row is **not** a same-size comparison: it is 2 vCPU / 4 GB against the arm64 row's 4 vCPU / 8 GB, and the results below should be read that way.

## Install steps and timing

```bash

mkdir -p ~/rakazo && cd ~/rakazo
curl -fsSLO https://raw.githubusercontent.com/elie222/rakazo/main/infra/compose/install-images.sh

# in .env: RAKAZO_IMAGE_TAG=edge -> v0.6.0 ; RAKAZO_COMPUTER_IMAGE_TAG=edge -> v0.6.0
bash install-images.sh                          # INSTALL_EXIT=0, 134 seconds
```

## Smoke test (scoped)

Passed at stack level, same scope as test 2: web UI reachable locally and over public HTTPS (200), `/health` 200, diagnostics clean. **A bot conversation was not run** — the test plan for this row is stack-level, the maintainers hold no model-provider credential, and using the operator's keys is out of scope. The 4 GB question this row can answer is therefore the install-and-idle one above, not behaviour under an active bot workload.
