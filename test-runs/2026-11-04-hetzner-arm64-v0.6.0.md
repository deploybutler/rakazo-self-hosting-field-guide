## Owner account baseline (default configuration)

With the installer defaults (no signup allowlist, no SMTP configured), the first account was created through the API and could sign in immediately:

```text
POST /api/auth/sign-up/email  -> HTTP 200 (user created, "emailVerified": false, session issued at once)
POST /api/auth/sign-in/email  -> HTTP 200 (signed in despite "emailVerified": false)
```

So on v0.6.0, email verification does **not** block sign-in in the default configuration — verification only blocks once a signup allowlist is configured (reproduced in the test 6 log). This differs from the October `edge` install, where the first owner was blocked by `Email not verified` under the then-default settings.

## Smoke test (scoped)

Passed at stack level: web UI reachable locally (200), API health 200, diagnostics clean, owner sign-up and sign-in working. **A bot conversation was not run**: the maintainers have no model-provider credential of their own for this test, and using the operator's keys is out of scope — so the bot-level smoke (memory + computer tool + time question) from the October run was not repeated here. Until a provider is connected in the app, a first bot message will fail for that reason alone; this log does not claim the bot path for v0.6.0 beyond the healthy stack underneath it.
