# Test run: 2026-11-04 — Hetzner CAX21 (arm64, Ubuntu 24.04) — Rakazo v0.6.0 pitfall reproductions (test 6)

- **Date (Europe/Berlin):** 2026-11-04
- **Tester:** DeployButler
- **Machine:** the same throwaway Hetzner CAX21 as the test 2 log (`2026-11-04-hetzner-arm64-v0.6.0.md`): arm64, Ubuntu 24.04.4 LTS, Docker 29.9.3 / Compose v5.7.0, Rakazo v0.6.0 published images (`app` sha256:b8719f74…, `computer` sha256:0c2800e6…)
- **Scenario:** Reproduce three first-install pitfalls on the fresh v0.6.0 install and verify the documented fixes: (a) email verification lockout with no SMTP, (b) loopback `WEB_ORIGIN` / unpublished port breaking non-local clients, (c) automatic recovery after a VPS reboot.

## (a) Email verification lockout with no SMTP — REPRODUCED, fix verified

Setup: the test-2 owner account existed but was unverified (`emailVerified: false`). `SMTP_URL` was empty (no email delivery configured — the installer default). `SIGNUP_ALLOWLIST` was then set to the owner's address in `.env` and the installer re-run (21 seconds), which is the documented way to restrict signups.

Sign-in attempt with the unverified account:

```text
POST /api/auth/sign-in/email -> HTTP 403
{"message":"Email not verified","code":"EMAIL_NOT_VERIFIED"}
```

That is the verbatim lockout from the October run: with an allowlist configured and no working email delivery, the owner cannot sign in and no verification email can ever arrive. (Baseline contrast, from the test 2 log: with **no** allowlist, v0.6.0 lets the same unverified account sign in — the lockout needs the allowlist condition on this release.)

Fix, using the documented no-email recovery command (`bootstrap-owner`):

```text
# First attempt, with prefixed variable names of our own invention
# (the guide and the CLI both use the unprefixed names further below):
$ docker compose -f docker-compose.images.yml exec -T \
    -e BOOTSTRAP_OWNER_EMAIL=... -e BOOTSTRAP_OWNER_PASSWORD=... \
    api node dist/cli/bootstrap-owner.js
Error: OWNER_EMAIL is required
```

**A mistake of ours worth recording:** the CLI reads the unprefixed names `OWNER_EMAIL` / `OWNER_PASSWORD` / `OWNER_NAME` — the same names the upstream accounts guide documents. Our first attempt (above) used `BOOTSTRAP_OWNER_*` names of our own invention, which the CLI does not read; hence the error. (An earlier version of this log wrongly called this a doc/build mismatch; the mismatch was ours, and the wording has been corrected.) With the correct names, the same command succeeds:

```text
$ docker compose -f docker-compose.images.yml exec -T \
    -e OWNER_EMAIL=... -e OWNER_PASSWORD=... -e OWNER_NAME=... \
    api node dist/cli/bootstrap-owner.js
Account verified

POST /api/auth/sign-in/email -> HTTP 200 ("emailVerified": true)
```

Result: **reproduced and fixed.** The guide's error-table row for `Email not verified` is updated from this run, including the allowlist condition and the variable-name caveat above.

## (b) Loopback origins / nothing published — REPRODUCED at server level, fix verified

Starting state (installer defaults): `BETTER_AUTH_URL`, `WEB_ORIGIN` and `API_URL` all `http://127.0.0.1:5173`, `RAKAZO_HOST=localhost`, and the web port bound to localhost only. From a different machine on the public internet, the VPS's public address served nothing at all:

```text
$ curl http://<vps-public-ip>:5173/  -> no answer (timeout, curl exit 28)
$ curl http://<vps-public-ip>/       -> no answer (timeout, curl exit 28)
```

That is the server half of upstream issue #2672 ("This device cannot reach the screen URL."): any non-local client — including the mobile app — has nothing reachable to connect to, and the origin the app would seal into screen capabilities is the loopback address. The mobile app itself was **not** tested in this run (no test handset available to the maintainers); the claim here is limited to the server-side condition and its fix.

Bonus confirmation on the way to the fix: with Caddy (v2.11.8) reverse-proxying the public hostname to the web port while `RAKAZO_HOST` was still `localhost`, the app answered with the verbatim error from the guide's error table:

```text
Blocked request. This host ("<public-host>") is not allowed.
To allow this host, add "<public-host>" to `preview.allowedHosts` in vite.config.js.
(HTTP 403)
```

Fix (the documented production configuration): set `BETTER_AUTH_URL`, `WEB_ORIGIN` and `API_URL` to the public `https://` origin and `RAKAZO_HOST` to the public host in `.env`, re-run the installer (28 seconds), keep Caddy as the TLS terminator:

```text
$ curl https://<public-host>/            -> 200, <title>Rakazo</title>  (also verified from a second, off-VPS network)
POST https://<public-host>/api/auth/sign-in/email -> HTTP 200
```

Result: **server-side condition reproduced; documented fix verified.** The public hostname used was a free `sslip.io` name derived from the machine's address; it is not recorded here because the machine was temporary and was deleted on 2026-11-04.

## (c) Automatic recovery after VPS reboot — VERIFIED

Pre-reboot state: all five long-running services up (four `(healthy)`, web plain `Up` — see the test 2 note), Caddy active, HTTPS sign-in working. The VPS was then rebooted from inside (`reboot`, 11:25:27 UTC).

```text
system boot: 11:25 UTC
containers StartedAt: 2026-11-04T11:25:54Z (restart count 0 — started once by
  Docker's restart policy at daemon startup, not crash-looped)
SSH reachable again: ~20 seconds after the reboot command
first web check after SSH returned: HTTP 200 immediately

Post-reboot verification (all without any manual intervention):
$ docker compose -f docker-compose.images.yml ps
  api / postgres / supervisor / worker: Up (healthy); web: Up
$ systemctl is-active caddy                      -> active
$ curl http://127.0.0.1:5173/                    -> 200
$ curl https://<public-host>/                    -> 200 (on-VPS and off-VPS)
POST https://<public-host>/api/auth/sign-in/email -> HTTP 200
Memory after reboot: 1.6 GiB of 7.5 GiB used
```

Result: **verified.** The full stack and the Caddy reverse proxy come back on their own after a VPS reboot; from reboot command to a verified working HTTPS sign-in took about a minute.
