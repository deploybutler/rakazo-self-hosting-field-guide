# Rakazo Self-Hosting Field Guide

How to self-host Rakazo: install Docker Engine 26 or newer on a Linux VPS, run the official published-images installer from `elie222/rakazo` (`bash install-images.sh --prepare-only`, set the public origins in `.env`, then `bash install-images.sh`), put HTTPS in front of port 5173, configure email delivery or use the server-side owner bootstrap, lock signups down, and verify the stack with `docker compose -f docker-compose.images.yml ps` and a first-bot smoke test. This guide records what was actually tested, on which machine, and what failed along the way — with a log file behind every claim.

> **Unofficial guide.** This is an unofficial, independent field guide maintained by DeployButler. It is not published by, endorsed by, or affiliated with the Rakazo project or its author. Rakazo is open-source software (Apache-2.0) by elie222; the upstream repository is https://github.com/elie222/rakazo and the upstream documentation wins wherever this guide and the docs disagree.

**Last logged test run:** 2026-11-05 (test 5: `edge` fresh install on Debian 13 and the issue #3268 reproduction attempt; see `test-runs/2026-11-05-debian13-edge-issue-3268.md`).

## Upstream-reported environments (not our test results)

The following comes from the upstream documentation, checked on 2026-11-04. It is reported here for orientation only and does **not** count as a test result of this guide.

- Published images are multi-arch (`amd64` + `arm64`), so arm64 hosts need no special tag. Source: [upstream self-hosting guide](https://github.com/elie222/rakazo/blob/main/docs/self-host.md)
- Requirements for the published-images path: Docker Engine 26 or newer (API 1.45+), the Compose plugin, curl, and OpenSSL. Source: [upstream self-hosting guide](https://github.com/elie222/rakazo/blob/main/docs/self-host.md)
- The default image channel is `edge` (main builds). Source: [upstream self-hosting guide](https://github.com/elie222/rakazo/blob/main/docs/self-host.md)
- Rakazo v0.6.0 was published on 2026-11-04. Source: [v0.6.0 release](https://github.com/elie222/rakazo/releases/tag/v0.6.0)

## Top common errors

Every row has a source. Rows marked `TODO: verify` describe behaviour documented in a source but not yet reproduced in one of our own test runs; the exact wording and the fix will be confirmed or the row will be removed when the corresponding test runs.

| Error (verbatim where available) | Cause | Fix | Status / source |
|---|---|---|---|
| `Email not verified` | With a non-empty signup allowlist, accounts must verify their email before signing in. If no email delivery (SMTP or another provider) is configured, the verification email never arrives and a new account is stuck at sign-in. This matches what happened in our 2026-10-24 test run. | Configure email delivery before enabling an allowlist or before the first signup (for SMTP: `SMTP_URL` and `EMAIL_FROM`). For an installation without email, use the server-side owner bootstrap described in the upstream accounts guide instead of public signup, and keep that installation on a trusted local network. One note from our own run: the bootstrap CLI reads `OWNER_EMAIL` / `OWNER_PASSWORD` / `OWNER_NAME`, exactly as the upstream accounts guide documents. Our first attempt used `BOOTSTRAP_OWNER_*` names of our own invention and failed with `OWNER_EMAIL is required` — an error of ours, not a doc/build mismatch. | Documented in the upstream accounts guide, checked 2026-11-04; reproduced in our own runs on 2026-10-24 and again on v0.6.0 on 2026-11-04 (test 6: sign-in returned HTTP 403 with this message once an allowlist was set and no SMTP was configured; the bootstrap fix was verified end to end; note that on v0.6.0 the lockout needs the allowlist condition — with no allowlist the same unverified account signs in). Sources: [upstream sign-in and accounts guide](https://github.com/elie222/rakazo/blob/main/docs/self-host-accounts.md), [our 2026-10-24 log](test-runs/2026-10-24-hetzner-arm64-edge.md), [our 2026-11-04 pitfalls log](test-runs/2026-11-04-hetzner-arm64-v0.6.0-pitfalls.md) |
| `Set SANDBOX_SUPERVISOR_TOKEN in .env` (Compose validation pattern: `Set ... in .env`) | A required secret in `.env` is empty. The published-images Compose stack requires `SANDBOX_SUPERVISOR_TOKEN` for every sandbox provider, and empty required keys fail closed at Compose validation time instead of starting insecurely. | Generate an independent random value, for example `openssl rand -hex 32`, set it in `.env`, and re-run the installer. Do not reuse another secret's value. | Wording from the upstream Compose file: `infra/compose/docker-compose.images.yml` at the v0.6.0 tag, lines 189 and 341, guards the value with `${SANDBOX_SUPERVISOR_TOKEN:?Set SANDBOX_SUPERVISOR_TOKEN in .env}`. Not reproduced in our runs — the installer generated the value in every run we performed. Sources: [upstream Compose file at v0.6.0](https://github.com/elie222/rakazo/blob/v0.6.0/infra/compose/docker-compose.images.yml), [upstream secrets checklist](https://github.com/elie222/rakazo/blob/main/docs/self-host-secrets.md), [upstream self-hosting guide](https://github.com/elie222/rakazo/blob/main/docs/self-host.md) |
| `Blocked request` | The public host name is not the one the web container expects. Upstream sets this via `RAKAZO_HOST`: the web app is a Vite preview that only answers for recognised hosts, and the three public origins (`BETTER_AUTH_URL`, `WEB_ORIGIN`, `API_URL`) must all be the same public HTTPS origin while `RAKAZO_HOST` is its bare hostname. Leaving the loopback defaults in place on a public server produces this failure. | Set `BETTER_AUTH_URL`, `WEB_ORIGIN`, and `API_URL` to the same public HTTPS URL, set `RAKAZO_HOST` to the bare hostname, re-run the installer, and recreate the web container if needed. | Verified in our own test run 6 on 2026-11-04: behind a Caddy reverse proxy with `RAKAZO_HOST` still `localhost`, the app answered HTTP 403 with the verbatim text `Blocked request. This host ("<public-host>") is not allowed.`; after setting the four values as documented and re-running the installer, the same address served the app over HTTPS (200). Sources: [our 2026-11-04 pitfalls log](test-runs/2026-11-04-hetzner-arm64-v0.6.0-pitfalls.md), [upstream self-hosting guide](https://github.com/elie222/rakazo/blob/main/docs/self-host.md) |
| No password-recovery option on the sign-in page (symptom, not an error message) | Forgotten-password recovery only appears when a transactional email provider is available. Password changes for a signed-in user do not need email configuration, but recovery from the sign-in page does. | Configure an email provider (`SMTP_URL` + `EMAIL_FROM`, or the Resend provider settings in the upstream accounts guide); the recovery option then appears. | Documented in the upstream accounts guide, checked 2026-11-04. Source: [upstream sign-in and accounts guide](https://github.com/elie222/rakazo/blob/main/docs/self-host-accounts.md) |
| `no configuration file provided: not found` (running bare `docker compose` in the install folder) | The published-images installer downloads and uses a non-default Compose file name, `docker-compose.images.yml`. Compose commands that do not pass `-f docker-compose.images.yml` do not target the installed stack. | Always pass the file explicitly, for example `docker compose -f docker-compose.images.yml ps`. | Exact wording verified in our test run 2 on 2026-11-04 (Docker Compose v5.7.0): bare `docker compose ps` in the install folder prints `no configuration file provided: not found`. File name documented in the upstream self-hosting guide, checked 2026-11-04. Sources: [upstream self-hosting guide](https://github.com/elie222/rakazo/blob/main/docs/self-host.md), [our 2026-11-04 v0.6.0 log](test-runs/2026-11-04-hetzner-arm64-v0.6.0.md) |
| `404` on the websockify request when opening a bot computer screen (issue title: `Screen/VNC connection fails with 404 — websockify token dropped by sealScreenCapability`) | Reporter analysis in upstream issue #3268: `sealScreenCapability()` seals the target websockify URL, which contains the token, into an encrypted capability, but when the server-side proxy decrypts the capability and forwards the request to websockify, the token is dropped. Websockify is started with `--token-plugin=TokenFile --token-source=/tmp/rakazo/desktop-targets`, so a request without a valid token gets a 404. The computer container itself is healthy (x11vnc and websockify/noVNC running). Reported on Debian 13, Docker 29.x, `edge` images, behind a reverse proxy. | No upstream fix or operator workaround is documented in the issue as of the check date. Do not apply an invented workaround; follow the issue for the upstream fix. | Upstream issue #3268, **open** when checked on 2026-11-04 (opened 2026-11-04) and still open with no comments when re-checked on 2026-11-05. **Our field result (test 5, 2026-11-05): not reproduced** on the `edge` build pulled that day (digests in the log) — the screen connected and a live desktop rendered; a tokenless direct request to the sandbox's websockify port did return 404, so the token check itself is in place. Scoped to that build; `edge` is a rolling tag. Source: [upstream issue #3268](https://github.com/elie222/rakazo/issues/3268); field log: [2026-11-05 Debian 13 / issue #3268 log](test-runs/2026-11-05-debian13-edge-issue-3268.md) |
| `Could not load the desktop. This device cannot reach the screen URL.` (mobile app, opening a bot computer) | Upstream issue #2672: `WEB_ORIGIN` defaults to `http://127.0.0.1:5173` and the screen capability is sealed for that origin verbatim. A phone cannot reach the server's loopback address, so the mobile WebView fails before any request reaches the server; the web client is unaffected because it re-hosts screen paths on its own origin. | Operator fix documented in the issue: set the public origin consistently — `RAKAZO_HOST` to the public host, and `BETTER_AUTH_URL`, `API_URL`, and `WEB_ORIGIN` all to the same public HTTPS origin — then the mobile app works unchanged. | Upstream issue #2672, closed when checked on 2026-11-04 (published 2026-10-29; the app-side fix landed in merged PR [#2671](https://github.com/elie222/rakazo/pull/2671), `fix(mobile): open computer screens sealed for unreachable origins`). Server-side condition reproduced and fix verified in our test run 6 on 2026-11-04 (with the loopback defaults nothing answered at the server's public address at all; after the documented origin change the app and sign-in worked over public HTTPS). The mobile app itself was not tested in that run — no test handset was available — so the app-side claim rests on the issue. ## Quick start

This is the shortest path that matches the upstream published-images flow and our October test run. The full, tested walkthrough is linked under "Need help?" below.

```bash
# On a Linux VPS with Docker Engine 26+ and the Compose plugin:
curl -fsSL https://get.docker.com | sh

mkdir -p ~/rakazo && cd ~/rakazo
curl -fsSLO https://raw.githubusercontent.com/elie222/rakazo/main/infra/compose/install-images.sh
bash install-images.sh --prepare-only   # generates .env; stop and edit it first

# In .env, before the first start:
# - Set BETTER_AUTH_URL, WEB_ORIGIN and API_URL to the same public HTTPS origin
# - Set RAKAZO_HOST to the bare hostname of that origin
# - Configure email delivery (SMTP_URL + EMAIL_FROM) or plan to use the owner bootstrap
# - Back up .env somewhere safe; the ENCRYPTION_KEY in it cannot be recovered if lost

bash install-images.sh                  # full install
docker compose -f docker-compose.images.yml ps   # api/postgres/supervisor/worker report (healthy); web shows Up
```

Then put HTTPS in front of `127.0.0.1:5173` (for example with Caddy), register the owner account, close public signups, take a baseline database backup, and run a first-bot smoke test (memory, a computer-tool task, and a time question) before calling the install done. For the secrets that must never leak or be lost, follow the upstream [secrets checklist](https://github.com/elie222/rakazo/blob/main/docs/self-host-secrets.md).

## FAQ

**Is this the official Rakazo guide?**
No. See the unofficial notice at the top of this page. The upstream documentation is the authoritative source.

**Which version should I install: `edge` or a release tag?**
The published-images example defaults to `edge`, which upstream describes as "`edge` (main builds)" ([self-hosting guide](https://github.com/elie222/rakazo/blob/main/docs/self-host.md)). A release tag such as v0.6.0 is a fixed point in time. This guide tests both: the October instance runs `edge`, and v0.6.0 fresh installs are logged on arm64 (matrix row 2) and on x86_64 (matrix row 4) (stack level; bot conversation not tested).

**Does Rakazo work on ARM servers?**
Our October test ran the full stack, including the browser sandbox computer image, on an arm64 Hetzner CAX21 and passed its smoke tests. Upstream also states that every publish is multi-arch (`amd64` + `arm64`), and the x86_64 fresh install of v0.6.0 is logged as matrix row 4 (2026-11-05, on a 2 vCPU / 4 GB machine — see that log for the sizing note).

**Why did my account get stuck at sign-in?**
Most likely email verification with no email delivery configured — see `Email not verified` in the error table above.

**What must I back up before an upgrade?**
At minimum the Postgres database and the `.env` file. A restored database is useless without the `ENCRYPTION_KEY` that encrypted it, and re-running the installer preserves an existing `.env` rather than rotating its secrets (see the upstream [secrets checklist](https://github.com/elie222/rakazo/blob/main/docs/self-host-secrets.md)). Our October rollback test restored a database backup in about a minute of service restart time after the restore itself; the full procedure is in the October log. Also record the running images' digests before the upgrade: `edge` is a moving tag, and our 2026-11-04 upgrade test found that a tag-level rollback landed on a newer `edge` build published the same day — the exact rollback needed the pre-upgrade digests (pulled from GHCR by digest and retagged) plus the database restore; see matrix row 3.

**Can I contribute a test run?**
Yes — see `CONTRIBUTING.md`. Test runs without logs, versions, and digests are not accepted.
